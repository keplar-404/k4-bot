# Backend (`apps/backend`)

A single Cloudflare Worker named `backend`, written in TypeScript with Hono. Entry point: `src/index.ts`.

## Layout

```
apps/backend/
├── src/
│   ├── index.ts            Hono app, global middleware, exports of every Durable Object and Workflow class
│   ├── routes.ts           Mounts each module's router under /api/v1
│   ├── scheduled.ts        Cron handler (every minute + daily)
│   ├── config/env.ts       zod schema of every variable and binding (parsed once per isolate)
│   ├── db/                 Drizzle client and schema (one file per area in db/schema/)
│   ├── middleware/         auth-guard, cors, rate-limit
│   ├── shared/             request context, zod validation, relay tokens, AES-GCM secrets, mail
│   ├── prompts/            Every prompt the backend sends to a model (one place to edit them)
│   └── modules/            Feature modules (below)
├── drizzle/                SQL migrations + snapshots (generated by drizzle-kit)
├── scripts/                One-off operational scripts (e.g. composio/set-webhook.ts)
└── wrangler.jsonc          Bindings: Durable Objects, Workflows, R2, rate limits, crons
```

## Modules

| Module | Responsibility | Key files |
|---|---|---|
| `auth` | Better Auth: email/password, Google, email verification, sessions; provisions a computer on verification | `auth.ts`, `limits.ts`, `email.ts` |
| `bots` | Bot CRUD, roles, model choice, per-bot apps/skills/MCP servers | `routes/`, `queries.ts`, `composio-apps.ts` |
| `chat` | Threads, messages, the durable chat run, the per-thread relay, stop/resume, quotas | `run/workflow.ts`, `run/slice.ts`, `relay/`, `threads.ts` |
| `agent` | Builds the agent for a run: model, tools, middleware, permission modes, approvals | `agent.ts`, `modes.ts`, `account-tools.ts`, `tools/`, `middleware/` |
| `async-tasks` | Background sub-agents that outlive the turn that started them | `workflow.ts`, `registry.ts`, `tools.ts` |
| `files` | R2 storage, uploads, reading PDFs / Office / text, OCR | `store.ts`, `documents/` |
| `memory` | Per-bot long-term memory and per-user preferences | `store.ts`, `routes.ts` |
| `computer` | One E2B desktop per user (Durable Object), live view proxy, screen tools | `user-computer.ts`, `durable/`, `routes/` |
| `sandbox` | One E2B code sandbox per bot, editor routes, exec policy | `index.ts`, `policy.ts`, `editor-routes.ts` |
| `integrations` | Skills (from skills.sh) and MCP servers: catalog, install, secrets, test | `catalog/`, `skills/`, `routes/` |
| `composio` | Connected apps: catalog sync, OAuth connect, tool lookup/execution, triggers, app events webhook, file staging | `execute.ts`, `triggers.ts`, `events-route.ts`, `verify-event.ts` |
| `workflows` | Workflow graphs, validation, publish, the run engine, live relay, public webhook | `graph/`, `engine/`, `store/`, `routes/`, `live/` |
| `schedules` | Shared schedule config and "when is it next due" (time zones, DST) | `config.ts`, `next.ts`, `issues.ts` |
| `tasks` | Scheduled bot tasks (Grok-style) | `store.ts`, `start.ts`, `due.ts`, `routes.ts` |
| `secrets` | The encrypted secrets vault used by workflows | `routes.ts`, `load.ts` |

Rules every module follows (see [Development guide](../guides/development.md)): files of at most 100 lines, routes
chained on one Hono instance (so types flow to the web), zod on every input, every query scoped to the session user.

## Durable Objects

| Class | Binding | One per | What it holds |
|---|---|---|---|
| `ChatRelayDurableObject` | `CHAT_RELAY` | chat thread | Gap-free event sequence, hibernating WebSockets, replay from `chat_event`, stop requests |
| `UserComputerDurableObject` | `USER_COMPUTER` | user | The E2B desktop: power state, sessions, daily meter, per-bot Linux accounts, control lease, activity feed |
| `BotSandbox` | `BOT_SANDBOX` | bot | The bot's code sandbox: lifecycle, idle pause, editor socket |
| `AsyncTaskRegistry` | `ASYNC_TASKS` | chat thread | Background tasks of a thread, their results and follow-up inbox |
| `WorkflowRunRelay` | `WORKFLOW_LIVE` | workflow | Live run events for the builders that have the workflow open |

All use the SQLite storage backend (`new_sqlite_classes` migrations `v1`–`v5` in `wrangler.jsonc`).

## Workflows (durable execution)

| Name | Class | What one instance is |
|---|---|---|
| `chat-run` | `ChatRunWorkflow` | One chat turn. A loop of bounded **slices**: each slice is a durable step that drives the agent for up to `RUN_SLICE_STEPS` graph steps, checkpoints to Postgres, and hands back. Approvals and questions are `waitForEvent` (up to 7 days); "come back later" is `sleep`. |
| `async-task` | `AsyncTaskWorkflow` | One background sub-agent (up to 15 minutes, no automatic retry so research is never paid twice). |
| `workflow-run` | `WorkflowRunner` | One run of a user's workflow: each block is a durable `step.do`, delays are `step.sleep`, approvals `step.waitForEvent`. |

Rule of thumb from Cloudflare's guidance, applied everywhere: every write happens inside a step, so a resumed instance
never repeats a finished side effect.

## Cron (`scheduled.ts`)

| Schedule | Work |
|---|---|
| `* * * * *` | Start due scheduled workflows (`workflows/engine/schedule.ts`) and due bot tasks (`tasks/due.ts`) |
| `0 3 * * *` | Prune chat events older than 7 days (keeping each thread's newest), refresh the Composio catalog, pause stale sandboxes, mark stuck runs failed, prune Composio event ids |

Every due item is **claimed** with a conditional update before it starts, so overlapping cron invocations never start
the same run twice.

## Global middleware (`src/index.ts`)

1. `corsMiddleware`: only `WEB_ORIGIN`, with credentials.
2. `secureHeaders` (except the computer stream, which sets its own framing headers; file bytes allow cross-origin `<img>`).
3. `bodyLimit` 1 MB.
4. `ipLimit` (100 requests/min per IP) on `/api/v1/*`, except auth (Better Auth limits itself), the computer stream
   (token-gated, ~60 asset requests per page) and Composio events (shared sender IPs; authenticated by signature).

## Prompts (`src/prompts/`)

Every text the backend sends to a model lives here, so it can be reviewed and edited in one place:

| File | Used for |
|---|---|
| `chat-system.ts` | The chat bot's system prompt (identity, mode, capabilities, apps, computer, memory) |
| `computer.ts` | The computer and files sections of that prompt |
| `roles.ts` | Role playbooks (assistant, advisor, writing, coding, custom) |
| `research.ts` | The research role's playbook and its sub-agent brief |
| `subagent.ts` | Members of a `spawn_subagents` group |
| `background-task.ts` | Background tasks |
| `commands.ts` | `/deep-research` and `/compact` |
| `workflow-tools.ts` | The block and reference help shown to bots that build workflows |
| `workflow-ai-step.ts` | The "Ask a bot" workflow step |
| `tasks.ts` | Scheduled tasks (schedule help, the message posted at each run) |

Tool descriptions stay next to their tools (they describe parameters and must change with them).

## Type sharing with the web app

`src/index.ts` exports `AppType`. The web app imports backend types through the `@backend/*` path alias (for example
`@backend/modules/workflows/graph/schema`), so a schema change shows up as a web type error at once.
