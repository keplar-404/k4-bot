# Grow K4's assistant from editor to debugger

K4 already has the right skeleton for a workflow-builder copilot: a LangChain `createAgent` with 20 custom tools, a durable Cloudflare Workflow loop, a Neon checkpointer and a live canvas. The main work left is not a rebuild. The assistant can edit and test, but it cannot see why a run failed, read or pin step data, or check that `{{steps.x.output.path}}` references are real. Almost every missing capability already exists as a backend function (`listRuns`, `getRun`, `recentHooks`, `listSecrets`, `nextRunAt`, `getTriggerType`, `isRead`) that no tool wraps yet. The recommendation is to stay on plain `createAgent` rather than switch to Deep Agents, keep the tool count near 30 with only about 15 shown per turn, and add a small set of tools in this order: run inspection, pins, reference and validation checks, then undo. The middleware stack should gain summarization, model retry, a model-call limit and a parallel-tools limit, and it should move the confirmation prompts into a declarative approval layer. Industry platforms (n8n, Make, Zapier, Power Automate, Activepieces) converge on the same design: small typed graph-edit tools, schema lookups, credentials handed off to a UI card, and visible undo. n8n alone feeds execution results back into the editing loop, and that loop is the largest gap in K4.

## What other platforms teach: small edit tools, validators, execution feedback

n8n's builder is the only one with inspectable source. It is a LangGraph graph in which a supervisor routes to a discovery-and-planning subgraph or a help subgraph, and a responder writes the reply, with deterministic nodes for compaction and error cleanup ([n8n source](https://raw.githubusercontent.com/n8n-io/n8n/master/packages/@n8n/ai-workflow-builder.ee/src/multi-agent-workflow-subgraphs.ts)). Its tools are single-purpose: add, connect, remove and rename node, update parameters, plus node search, details, examples, `validate_structure`, `validate_configuration`, `get_execution_logs`, `get_execution_schema`, `get_expression_data_mapping` and `submit_questions` for asking the user ([n8n tools](https://github.com/n8n-io/n8n/tree/master/packages/@n8n/ai-workflow-builder.ee/src/tools)). Two design choices matter for K4. First, validation is a tool the agent calls, so it can self-correct inside its loop instead of failing at a final gate. Second, execution-aware tools let the agent map real upstream output fields into expressions, so test runs feed edits. K4's own backend has the run data but gives the model only a status and the last three outputs. n8n also uses a secondary LLM chain to fill node parameters from a schema filtered by version, resource and operation, and it checks the output structure afterward ([n8n update tool](https://raw.githubusercontent.com/n8n-io/n8n/master/packages/@n8n/ai-workflow-builder.ee/src/tools/update-node-parameters.tool.ts)). K4's equivalent is `get_action_details` plus server-side validation of `config`, so no second model call is needed.

The closed platforms show the product-level patterns. Make's Maia is a single agent calling predefined tools sequentially, with each change shown live on the canvas and the tool calls listed in chat. It never runs, activates or deactivates scenarios, never touches credentials (a connection card collects them outside the chat), and can revert to a prior version from chat ([Maia system card](https://help.make.com/maia-by-make-system-card)). Zapier Copilot offers an explicit autonomy toggle, "Auto-build" versus "Ask as you build", plus checkpoints, Undo and Versions, and it warns that long chats overflow context and degrade accuracy ([Zapier best practices](https://help.zapier.com/hc/en-us/articles/45327353705997-Best-practices-for-using-Zapier-Copilot)). Power Automate Copilot is deliberately narrow: a subset of connectors, no error fixing, and changes the user must review and can undo ([MS Learn FAQ](https://learn.microsoft.com/en-us/power-automate/faqs-copilot)). Activepieces Chat asks which account to connect and lets the user review every step before publishing ([Activepieces docs](https://www.activepieces.com/docs/ai/chat.md)). K4 already matches Maia on credentials (`request_app_connections`) and on live canvas updates. It trails on undo, on an autonomy toggle, and on execution feedback. One caution: no vendor has published quantitative evals for its builder, so none of these designs is proven better by data. Pipedream, Gumloop, Retool and Langflow were not researched, so the "industry consensus" rests on five platforms.

## Tool design rules the K4 toolset should follow

The tool-design literature supports K4's recent fixes and sets the rules for new tools. Anthropic advises a few purpose-built tools over thin API wrappers, namespaced names, high-signal responses with a concise/detailed option, truncation that tells the agent how to narrow its search, and errors that show a correct input ([Anthropic, Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)). OpenAI suggests staying under about 20 functions at the start of a turn, using enums so invalid states are impossible, and not asking the model for values the code already knows ([OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling)). Tool selection degrades past 30 to 50 tools, and tool search raised one MCP eval from 49% to 74% for Opus 4 ([Anthropic, Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)). Usage examples raised complex-parameter accuracy from 72% to 90% in the same source.

K4 has already applied the right lessons. Block `kind` is a fixed enum, action search ranks by matching words with a plural strip and a double weight for name matches, a no-match search returns the first 25 actions so the model picks from real ones, and `config` accepts a JSON string. These fixes remove wasted calls through the schema and a fallback list, not prompt text, and new tools should do the same. Tool schemas are checked for JSON-Schema conversion in `tools.check.ts`, which guards against zod transforms (confirmed to throw "Transforms cannot be represented in JSON Schema" in the installed zod). Keep schemas flat, with string enums and nullable fields rather than `anyOf`, because Gemini and DeepSeek through OpenRouter have rejected unions that OpenAI accepts ([pydantic-ai issue](https://github.com/pydantic/pydantic-ai/issues/3617)). Do not make Composio's arbitrary action schemas tool parameters; pass `config` as a loose object or JSON string and validate it server-side against the fetched action schema.

Editing should stay ID-addressed. Research on JSON editing found that patch-style edits cut tokens by 31% with quality within 5% of full regeneration, but that models miss related updates and break on array index shifts, which stable-ID keys avoid ([JSON Whisperer](https://arxiv.org/abs/2510.04717v1)). K4's `add_block`, `update_block`, `remove_block` and `connect_blocks` already work this way, and every edit passes through `edit()`, which validates and saves with an optimistic `updatedAt` check. Keep `set_workflow` and `import_workflow_json` as bulk fallbacks only, and confirm before they replace a non-empty draft. For small or free models, small models collapse on multi-turn tool use (Qwen3-4B scores 62% overall on BFCL but 35% multi-turn) ([TinyLLM paper](https://arxiv.org/pdf/2511.22138)), so the plan is fewer tools per turn, server-injected IDs, a short graph summary re-injected each turn, and capped steps. There is no controlled study of plan-then-act for graph editing, so that remains a design bet.

## Framework and middleware: stay on createAgent, add four middleware, move confirmations to a declarative layer

Deep Agents (`createDeepAgent`) adds planning, a virtual filesystem, subagents and summarization on top of `createAgent`. A fixed-toolset workflow assistant gains little from the filesystem, because the graph JSON is the document and custom tools (`get_workflow`, `update_block`, `validate_workflow`) are a cleaner interface than file reads and writes. No official page compares the two directly, so this is an inference, but it matches how n8n and Make expose the graph. Keep `createAgent`. Reconsider Deep Agents only if you add a research or "build a whole workflow from a long spec" mode, where a subagent keeps big catalog results out of the main context. K4's design doc already deferred subagents, filesystem and computer tools to "later".

The installed `langchain` 1.6.3 ships about 22 prebuilt middleware, and K4 uses only a few of them ([built-in middleware](https://docs.langchain.com/oss/javascript/langchain/middleware/built-in)). The current stack is tool-errors, tool-retry (read-only tools only), `todoListMiddleware`, a todo guard, `toolCallLimitMiddleware({runLimit: 120, exitBehavior: "continue"})` and `piiMiddleware` for credit cards and API keys. The bot chat agent, by contrast, has summarization at 80% of the context window, a parallel-tools limit and vision routing. The assistant's history is the checkpointer thread `assistant:<threadId>`, which grows without compaction, so long builds on small-context models will overflow, which Zapier also warns about. The recommended additions are as follows.

- **Summarization.** Add `summarizationMiddleware` with a `trigger` (it is off unless set) such as 70 to 80% of the context window, `keep: {messages: 20}`. Reuse the bot's `createSummarizeMiddleware` only if it runs without a Deep Agents backend; this was not checked. Pair it with re-injecting `describeWorkflow` into the system prompt each turn, which K4 already does with a 12,000-character cap, so the graph never depends on compacted history.
- **Model retry and fallback.** `modelRetryMiddleware` handles transient provider errors, and `modelFallbackMiddleware(...)` (fallbacks only, tried in order) suits the free-model scenario. Put fallback before any refusal handling. `modelRefusalMiddleware` needs langchain 1.6.4 or later and is not in the installed 1.6.3.
- **Model-call limit.** `modelCallLimitMiddleware({runLimit, exitBehavior: "end"})` bounds loops on weak models. It complements the existing tool-call limit, whose `"continue"` behavior only blocks excess calls rather than ending the run.
- **Parallel-tools limit.** Reuse `createParallelToolsMiddleware` from the bot stack, so two edits do not race on the same draft.
- **Human-in-the-loop.** K4 puts `interrupt()` inside `turn_on_workflow`, `share_with_bots` and `request_app_connections`. `humanInTheLoopMiddleware` with `interruptOn` gives approve, edit, reject and respond decisions declaratively, so adding confirmation to `turn_off_workflow`, `import_workflow_json`, `set_workflow` and `cancel_run` becomes a config line. Keep `interrupt()` inside `request_app_connections` and a new `ask_user`, because those need custom cards. On resume the node restarts from the top, so code before `interrupt()` must be idempotent (local langgraph-human-in-the-loop skill). Tool errors that are interrupts always pass through `toolErrorMiddleware`.
- **Optional.** `contextEditingMiddleware` (clears old tool results; defaults to 100k tokens, keep 3) is a cheaper alternative to summarization for run-heavy debugging threads. `llmToolSelectorMiddleware` is worth adding only if the toolset passes about 30 tools. `anthropicPromptCachingMiddleware` helps if the production model is Anthropic, since the system prompt (rules, BLOCKS_HELP, TEMPLATES_HELP) is large and stable.

Order caveat: the notes did not verify whether the first middleware in the array is the outermost wrapper, so check ordering with a test before relying on it. Suggested order: tool-errors, tool-retry, model-fallback, model-retry, model-call limit, summarization, todo list, todo guard, parallel-tools limit, tool-call limit, HITL, PII.

For memory, short-term memory is the Neon checkpointer, which already works over HTTP through a custom `NeonHttpCheckpointer`, because the stock Postgres saver is believed to need a raw TCP socket (a repo comment; not verified externally). Long-term memory today is one 8,000-character blob per user, replaced in full by `save_memory`. A LangGraph-style store keyed by namespace such as `[userId, "memories"]` is the documented pattern ([long-term memory](https://docs.langchain.com/oss/javascript/deepagents/long-term-memory)). The proportionate step for K4 is to keep the blob but make writes append or patch rather than replace (so the model cannot erase memory by mistake), and move to a keyed table later. Add `batch` writes for checkpoint `put` and `putWrites`, since Neon HTTP supports non-interactive batches but not interactive transactions ([Neon driver](https://neon.com/docs/serverless/serverless-driver)).

## The runtime already fits Cloudflare; harden four places

The slice design maps well onto Workflows: steps are cached by deterministic name, waiting instances do not count toward concurrency, and Paid limits are generous (10,000 steps by default, up to 25,000) ([Workflows limits](https://developers.cloudflare.com/workflows/reference/limits/); [Rules of Workflows](https://developers.cloudflare.com/workflows/build/rules-of-workflows/)). The assistant uses `slice-${n}` and `answer-${n}` step names, `waitForEvent` for confirmations (up to 7 days), `retries.limit: 0` for non-idempotent canvas edits, and a Durable Object relay for live updates. That is compliant, and the Agents SDK's `AIChatAgent` would trade away Postgres as the source of truth for built-in resumable streaming, so it is not worth a migration now ([Chat agents](https://developers.cloudflare.com/agents/agent-class/communication-channels/chat/chat-agents/)). Four hardening points follow from the notes.

First, tool calls are never streamed to the user; they see only todos, the canvas and the final answer. Make and n8n both show tool calls or phases, and for a debugging assistant that reads runs this transparency matters. Add a compact tool-call event (name, target block, result) to the DO relay with a sequence number so a reconnecting client can replay it. Second, the stop signal is polled from Neon every 1.5 seconds, about 800 queries per 20-minute slice; a stop flag held in the DO relay would cut that. Third, the daily token budget is checked at slice start, so one slice can overshoot, and `MAX_SLICES = 40` at 20 minutes each allows roughly 13 hours of agent time; add a per-run token cap and lower the slice count. Fourth, the active-run check was a check-then-act race; per the task brief it is now being fixed, and a partial unique index on active statuses is the durable form of that fix. On the web side, AI Elements maps cleanly onto the existing pieces (Plan/Task/Queue for todos, Confirmation for waiting questions, Tool for the new tool-call events, Checkpoint for undo points), and installation should come from the shadcn registry because the standalone site is slated for deprecation at the end of November 2026 ([AI Elements](https://elements.ai-sdk.dev/)). Better Auth and Hono need no changes beyond keying rate limits on the user: Cloudflare's rate-limit binding is per-location and approximate, so strict caps belong in Postgres or a Durable Object, which K4 already does ([Rate limit binding](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)).

### Recommended middleware stack

Outermost to innermost, to be confirmed by an ordering test: tool-errors; tool-retry on read-only tools (now including `get_run`, `list_runs`, `list_secrets`, `list_connected_apps`); model-fallback (free-model scenario); model-retry; `modelCallLimitMiddleware` with `exitBehavior: "end"`; `summarizationMiddleware` (trigger near 70 to 80% of context, keep 20 messages); `todoListMiddleware` and the todo guard; parallel-tools limit; `toolCallLimitMiddleware` (run limit kept at 120, or lowered); `humanInTheLoopMiddleware` on turn-off, set, import and cancel (existing `interrupt()` cards stay); PII middleware. Add prompt caching if the production model is Anthropic.

### Known bugs and weaknesses

Fixed since the audit, and now part of the baseline: the Return block has no output connection; tool schemas avoid zod transforms (checked by `tools.check.ts`); action search is ranked by words; block kinds are a fixed enum. Fixed in parallel work: `test_workflow` trigger input shape for webhook, schedule and app triggers (it wrapped inputs as `{inputs}` instead of the route's shapes); `update_block` shallow merge (nested `arguments` were replaced whole); the non-atomic active-run check (two concurrent starts could both pass). Each should get a regression test before further tool work, because the new `get_run` and `pin_output` tools depend on correct trigger input.

Still open, in order: (1) `test_workflow` has no `pins` parameter and cannot pin an output after a run; (2) `waitForRun` returns only status, error, failed block and the last three outputs, and its timeout message points to `workflow_run_status`, a tool the assistant does not have; (3) `turn_off_workflow` has no confirmation; (4) no summarization, so threads grow without limit; (5) no check that template references exist, which is the main source of silent logic bugs (Make's card names logic bugs as a known limit); (6) no undo; (7) tool calls are not streamed to the user; (8) the stop poll and the slice-start-only budget check. Not checked in the audit: the full text of BLOCKS_HELP and TEMPLATES_HELP, whether a draft-version table exists, and whether the bot's summarize middleware runs outside Deep Agents.

## Conclusion

The surprising finding is how little new infrastructure the assistant needs. The platforms that look most capable, n8n above all, differ from K4 less in architecture than in closing the loop: validate as a tool, read execution data, and map real fields into references. K4 holds every ingredient for that loop in code that exists today, so the work is roughly a dozen thin wrappers plus one new check, reference validation, which has no backend equivalent yet and must be ported from the web data picker.

Two decisions follow. Gate by phase rather than by adding a tool-selector model, because 38 tools exceeds the 30 to 50 degradation range. And move write-safety into code (`isRead` plus HITL) instead of prompt rules, since a free model will eventually test a send step. The open question the notes cannot answer is quality: no vendor publishes builder evals, so K4 should build its own set of 20 to 50 tasks from real failures, graded on the final graph (valid, right slugs, right edges, no invented slugs) and run on both free and paid models, using pass-all-k scoring ([Anthropic, Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). That will show which of the P1 and P2 tools are worth their prompt cost.
