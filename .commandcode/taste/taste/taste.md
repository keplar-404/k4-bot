# Taste
- Prefers the agent to build complete context up front before receiving/starting a task: read the entire project first, each and every individual file (structure, tech stack, and how frontend and backend connect), including every file in `.agents/skills` — "don't skip anything", "read each and individual every file's full context and load into your context" — then wait for the task instead of jumping into changes. Confidence: 0.9
- Wants a detailed, flow-oriented plan (current flows, how it should be done well, best practices) for approval before implementation, not a bare task list. Confidence: 0.8
- Requires a research-first workflow: read the relevant skills and current official documentation, using MCP and online research when available, before planning or writing code; do not guess APIs or rely on potentially outdated training knowledge. Confidence: 0.95
- Implements only what is explicitly requested: do not add Cloudflare service integrations, API routes, or other wiring beyond the scoped task; when asked to scaffold or change something in a specific folder, modify only that folder (e.g., scaffold the deep agent with OpenRouter in the agent folder only); and do not alter existing UI/design (e.g., loading skeletons, layouts) unless explicitly asked — keep visual behavior unchanged. Confidence: 0.95">
- Efficiency-minded about API usage: "don't over call the api" — dedupe/cache repeated frontend fetches (e.g. module-level promise cache + invalidation after mutations, Next.js component caching) and backend caching (KV/edge), and rate-limit backend endpoints rather than letting clients refetch freely. Confidence: 0.75
- Environment variables must come from the centralized `/lib/env.ts`; prefer importing the ready-to-use `env` singleton object (e.g. `import { env }`) over calling `parseEnv`, and never read `process.env` directly. Workers still call `parseEnv(c.env)` with their bindings. Confidence: 0.9">
- Follows SOLID principles in code changes. Confidence: 0.75
- Before adopting a third-party npm package, audits its installed files (package.json and dist) for malicious/suspicious code (eval, fetch, child_process, fs, process.env, cookie/storage access, etc.) and confirms it is safe before wiring it into the project. Confidence: 0.9
- For platform/service cards, prefers full-color brand logos (not monochrome icons or text/letter fallbacks) with no background container around the logo, and a flat single `Card` (no `CardHeader`/`CardContent` subcomponents) using an internal 3-column grid — column 1 = logo, column 2 = title + description (takes the bigger/flexible space), column 3 = action button — with all items aligned to the top. Dark-toned logos (e.g. GitHub, Notion, X.com) should be inverted in dark mode (e.g. Tailwind `dark:invert`) so they stay visible, while colorful logos are left unchanged. When a real brand logo can't be resolved, do not present a text/letter placeholder as the logo; use the actual company logo (e.g. from the provider's official API/CDN) or an appropriate fallback treatment instead. Confidence: 0.95
- Right sidebar open/closed state should persist in `localStorage` (initialized to `true`) and update on every open/close or resize; opening a file from chat should automatically open the right sidebar. Confidence: 0.9
- Prefers implementation work delivered as complete end-to-end phases rather than incremental or partial phases ("not half or small phase", "Full phase work. a to z"); track outstanding items in a todo list and work them one by one, marking each done as completed; do not give periodic status reports listing remaining work — carry the task through to completion and report only once everything is finished ("After all the work is finished nothing is left then tell me that work is done").
